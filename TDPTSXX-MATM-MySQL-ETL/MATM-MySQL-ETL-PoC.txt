1. The idea (why this exists)
MATM data lives in a MySQL replica (microservice databases behind Manhattan Active). We need that
data in the lakehouse on a schedule — not as one-off notebooks, but as a repeatable ingestion product.
What we are implementing
A MySQL → Delta / Unity Catalog ingestion framework where:
1.
Connection details and credentials live in one shared stub.
2.
Each table/entity is defined in JSON (SQL, keys, target paths).
3.
One runner drives every entity through the same three stages: Extract → Transform →
Completion.
4.
Jobs support daily full and hourly/transactional incremental loads.
5.
Writes land in Unity Catalog and ADLS Delta (primary + secondary region).
Goals
•
Pull MATM MySQL databases into Delta / UC reliably.
•
Keep business logic in configs, not hardcoded notebooks.
•
Reuse the same notebooks for every new table.
•
Track incremental watermarks via loadtracker.
•
Deploy as a Databricks Asset Bundle (dev / tst / stg / prd targets).

–
Loadtracker catalog / schema / table
2.
MySQL JDBC jar is attached via MySql_Jdbc_Jar_Path.
3.
Entry notebook: Entity_Sequential_Runner.
4.2 Sequential runner
1.
Loads source JSON (entities map).
2.
Resolves which entities to run (entity_name widget empty = all; otherwise that entity +
dependencies).
3.
Ensures loadtracker table exists.
4.
For each entity, calls Entity_Pipeline_Worker with the same paths + that entity name.
5.
Aggregates successes / failures; fails the job if any entity failed.
4.3 Per-entity pipeline worker
Runs three notebooks in order:
 Extracts_Wrapper  →  Transforms_Wrapper  →  Completion
4.4 Extract
1.
Read entity extract.query_by_env for current Databricks_Env.
2.
Build JDBC options from entity jdbc + mysql_source_stub (connection_source: target_config).
3.
Optional incremental: if incremental.enabled and load_mode=transactional, append watermark
predicate using last successful load from loadtracker (or fallback MAX on UC table).
4.
spark.read.format("jdbc") → create temp + global temp views (mysql_extract_*).
4.5 Transform
1.
Read extract global temp view.
2.
If transform.query_by_env is set → run that Spark SQL.
3.
Else → passthrough (same columns/types as extract).
4.
Publish mysql_transform_* views.
4.6 Completion
1.
Resolve Delta / UC paths from entity target.*_by_env.
2.
Dedupe on configured keys if needed.
3.
Write Raw + Transform layers (primary + secondary region paths/catalogs).
4.
Update loadtracker when incremental watermarks apply.
5.
Hourly path can bootstrap a missing transform table with a full extract first.

Why stub + entity split?
•
One MATM host / credential set for all microservice DBs.
•
Each entity overrides which MySQL database/schema via jdbc.database_by_env (e.g. one entity
per MATM service DB).
Prerequisites on the workspace
•
Network path from job cluster to 10.219.252.18:3306
•
Secret scope mysql-replica with username and password
•
MySQL connector JAR on the UC volume path referenced by MySql_Jdbc_Jar_Path

9. How to add a real MATM business table
1.
Identify MySQL database name (MATM microservice) and table.
2.
Copy an entity block in mysql_extract_daily.json (and hourly if needed).
3.
Set:
–
jdbc.database_by_env → that microservice DB
–
extract.query_by_env → explicit column SELECT (avoid SELECT * for schema validation)
–
schema.columns matching the SELECT list
–
target.primary_key_columns / dedupe columns
–
target.target_entity naming convention (TDPS_Matm...)
–
Incremental watermark column if hourly
4.
Deploy bundle; run job with entity_name=<YourEntity>.
5.
Validate UC table + Delta path + loadtracker row.
No new Python notebooks required for a standard ingest.
